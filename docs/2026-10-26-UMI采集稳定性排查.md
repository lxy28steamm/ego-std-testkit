## 1. 一句话结论

今天香橙派 UMI 采集**全天 9 起失败**，每起都是「worker（采集工作进程）抛异常 → 自动重启 → 系统自动停止采集并删除没写完的 .mcap.partial」。失败模式不止一种：**8 起是视频队列被填满（queue is full，其中 7 起在开录 38-61 秒、1 起录到 54 分钟才爆），1 起是 JPEG 帧损坏**；另有 **10:55 USB SSD 物理掉线一次**、VIVE 定位器进程反复退出 52 条。**不是相机接错**——串口绑定、传感器状态、USB 连接全部正常。

大白话解释「队列满」：相机每秒产生 30 帧视频，这些帧先堆进一个缓冲队列（容量 8192 条），等程序排队写盘。如果写盘/处理速度跟不上产生速度，队列越堆越满，满到最后程序直接报错罢工。就像餐厅传菜口一次只能放 8192 个盘子，厨师炒得慢、传菜口堆满，就得摔盘子不干了。

## 3.5 JPEG 帧损坏根因分析（18:14 那次，18:38 补挖闭环）

### 直接原因（docker 崩溃栈实锤）

容器日志里抓到了完整 traceback：

```
Traceback (most recent call last):
  File "/usr/local/lib/python3.11/multiprocessing/process.py", line 314, in _bootstrap
  ...
    sample = adapter.read()
  raise RuntimeError("; ".join(errors))
RuntimeError: invalid UMI JPEG header
```

`adapter.read()` 是从相机读一帧 JPEG。JPEG 文件开头应该是 `FF D8` 两个字节（行话叫 SOI 标记，相当于 JPEG 的"营业执照"）。程序读到一帧开头不是 `FF D8`，认定这帧是坏数据，**直接把整个 worker 干掉**——没有任何容错，一帧坏 = 整条采集挂。

### 帧为什么坏——三层证据

**证据 1：相机全是 USB 相机，带宽已经打满**

| 事实 | 数值 |
|---|---|
| 相机型号 | DECXIN Camera（Sunplus 公模，USB ID `1bcf:2d4f`），非工业级 |
| 输出格式 | MJPEG，**3200x1296**（双目叠图：左 1600x1296 + 右 1600x1296 拼一张）@30fps |
| 估算单帧大小 | 0.4~0.8MB |
| 四路合计带宽需求 | 48~96MB/s |
| 实际可用 | **全部挤在 USB 2.0（480Mbps ≈ 60MB/s 理论，实际有效 35~40MB/s）**，还经过 Genesys 4 口 hub 转接 |

四根水管往一根吸管里灌水，必然有数据被挤断。帧数据在哪断，哪帧开头就缺字节，header 校验当场挂。

**证据 2：UVC 驱动全天有 URB 级错误**

```bash
dmesg -T | grep -i uvc | tail
```

做完应该看到两条 `Failed to resubmit video URB (-1)`（09:47:20、17:45:54）。URB 是 USB 传输的基本包裹；"重提交失败" = 内核没能把新的取图请求挂回链路 = USB 链路本来就有错。出错的还是第三只相机（USB20 WEB CAMERA），说明整条 USB 链路不健康，不止 DECXIN。

**证据 3：坏帧时刻四路相机同时丢 raw 帧**

```
UMI right/stereo  hardware: frames=30989 raw_captured=30990 raw_missing=1
UMI right/fisheye hardware: frames=30985 raw_missing=1
UMI left/stereo   hardware: frames=30999 raw_captured=31000 raw_missing=1
UMI left/fisheye  hardware: frames=30997 raw_missing=1
```

四路同时 `raw_missing=1`，且全天只出现这一次——不是某只相机固件偶发抽风，是坏帧时刻整个 USB 采集链路被同时扰动。

### 排除项

| 怀疑对象 | 排除依据 |
|---|---|
| SSD 写盘慢导致帧坏 | header 校验发生在**读相机时**（写盘之前），盘再慢也不会让已收到的帧开头烂掉。SSD 是放大器不是凶手 |
| 相机物理掉线 | 18:14 前后 dmesg 无 USB disconnect/reset |
| xHCI 报错（18:14:57 `unknown event type 37`） | 时间在崩溃后 2 秒，是 worker 死掉后 USB 栈清理残留传输的连带现象——是结果，不是原因 |

### 为什么队列满是主流、坏帧只 1 起

同一个病因（USB 带宽吃紧）的不同严重度：轻则帧在缓冲区里堆积（queue is full，7 起），重则帧数据在 USB 传输中被截断（坏帧，1 起）。**修带宽两个病一起好。**

### 怎么验证（最快实验，设备上直接能做）

相机本身就支持降档（`v4l2-ctl --list-formats-ext` 已列出）：2560x720@30fps 或 3200x1296@20fps，带宽降 1/3~1/2。跑 30 分钟，看坏帧和队列满是否消失。**这是确认根因成本最低的一刀。**

## 5. 固化了什么（本工作台内）

### 5.1 新脚本：`umi_stability_check.py`（可复跑）

一键检查 = API 实时状态 + SSH 日志历史扫描，输出通过/失败/待确认 + 证据 JSON（存 `out/`）。

```bat
set OP_SSH_PW=你的SSH密码
python umi_stability_check.py --host 192.168.50.164
```

- `--host`：**必改**（每台设备 IP 不同；也可以写进 `device_ip.txt` 省得每次带）
- `OP_SSH_PW`：**按情况**（不提供就跳过日志扫描，只查实时状态；密码走环境变量，不落在命令行和历史里）
- 其余参数：**不用改**

检查项与判定：

| 检查项 | 通过条件 | 不过说明什么 |
|---|---|---|
| UMI-ONLINE | 在线+硬件连接+worker running | 设备没连上 |
| UMI-WORKER-RESTART | 本次启动后重启 0 次 | ≥1 次 = 本轮发生过异常重启，当前健康也不算稳 |
| UMI-QUEUE | 录制中且水位 < 50% | 超过 = 正在积压，离爆满不远 |
| UMI-STREAM-MISSING | 各流 missing_count = 0 | >0 = 有帧序号空洞 |
| UMI-DISK-LATENCY | 只记录不判定 | >300ms 记录（USB SSD 常态 ~700ms） |
| UMI-SENSOR | state=ready 且必需侧全 valid | 手柄传感器没就绪 |
| UMI-LOG-HISTORY | 当天无删数据事件 | 有几起、什么模式、删了哪个文件，全列出（锚点=「异常采集已停止并删除」行，模式向前归因到最近的 worker_exception，避免同秒匹配漏事件） |

### 5.2 验收用例新增一条

`orangepi_acceptance.py` 增加 `ACC-stability`（采集稳定性）：跑验收时自动读队列水位 + worker 重启次数 + 会话状态，invalid/fault 或重启过的直接判失败，不再被"当前在线"蒙混过关。

### 5.3 排查路径沉淀（给下次的自己）

遇到「采集失败/数据被删」，按这个顺序查，不要一上来就怀疑相机：

1. `umi_stability_check.py --host <ip>` 一把看全貌
2. 失败 → 看 `UMI-LOG-HISTORY` 列出的时间和模式
3. 按时间去 grep 日志原文（见第 4 节命令）
4. 队列满 → 查写盘（iostat / disk_latency）和开录时机；
   JPEG 损坏 → 根因基本锁定 USB 带宽饱和，按 3.5 节验证；VIVE 失败 → 查定位器 USB 和标定文件
